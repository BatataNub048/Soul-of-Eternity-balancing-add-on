## Ares-family components

- **Infernum `AresEnergyKatana` (snapshot 1325).** `AresBodyBehaviorOverride.PreAI` creates two at opposite side values during authoritative arm creation (IL_03FD–0482). It supplies the original Calamity Ares body index and sets `realLife` to that same parent. `AresEnergyKatana.KatanaIsInUse` controls vulnerability. Exo combo attack code includes the katanas among affected Ares arms. The ordinary player route is the parent Exo Mechs fight with Infernum’s Ares override in effect. WoTM’s competing AI can affect which version runs. The katanas are NPC attack participants with no independent encounter or completion predicate established.
- **WoTM `AresHand` (snapshot 1550).** `AresBodyBehavior.NPCOverrideID` resolves to Calamity’s `AresBody`. Its AI calls `CreateArms` once on the authoritative side. The method creates four hands with the parent NPC supplied as the spawn start, and the hand AI sets `realLife` to `CalamityGlobalNPC.draedonExoMechPrime`. The hand uses the parent’s instructions and has a parent-dependent death path. This is a separate mod’s component type from Infernum’s katana and the already-grouped `FargowiltasCrossmod/AresHand`. All three belong to the Exo Mechs group.
- **Configuration.** WoTM’s override manager disables its overrides when Fargo Eternity is active and its `FargosDLC` reference to `FargowiltasCrossmod` is present. WoTM’s `InfernumOverridingSystem` temporarily clears the Infernum flag during detected Exo Mech updates and drawing and has restoration paths after projectile update, drawing and save/quit. Which components actually appear under each supported configuration remains a runtime question. The route uses the existing Draedon encounter with its Codebreaker and mech selection.

Calamity’s native `CalamityMod ExoMechs` declaration passes Apollo, AresBody, Artemis and ThanatosHead. It uses `Downed.DownedExoMechs` and supplies no custom availability predicate. The two audited component types are absent from those arguments. Neither inspected integration registers the two types or adds them to the entry. Actual finalized membership after all mods run remains unverified.

## Bereft Vassal and Great Sand Shark

`ColosseumPortal.RightClick` opens the Lost Colosseum portal when the player possesses `CalamityMod/SandstormsCore`. The interaction checks inventory and leaves the core in place. Portal proximity advances the transition and `NearbyEffects` requires Infernum custom AI before entry. `LostColosseumEntrance.Generate` has a worldgen call site and a fallback registered by the Cultist override’s kill event for worlds without a generated entrance. The generator starts from the Underground Desert and uses the Sunken Sea lab anchor in its Golem-down branch. These paths establish a source-defined route for eligible worlds. Actual portal placement or recovery in a particular existing world remains unverified.

`SandstormsCore.AddRecipes` supplies a Calamity recipe, and Infernum’s `RecipeUpdatesSystem.AddRecipes` calls its ingredient-adjustment helper for the core. Crafting and inventory acquisition in the pinned pack remain unverified. Infernum’s `UseRestrictionGlobalItem.CanUseItem` blocks direct summon use of the core with custom AI enabled. The portal uses possession. Inside Lost Colosseum, `WorldUpdatingSystem.PostUpdateEverything` creates the Vassal with a world-event source once per visit on the authoritative side when the local player is alive (IL_0115–0183). Vassal AI uses the arena boundary at X=18,400 for its outside check. Cultist defeat is an explicit **Checklist availability** gate. The spawn branch itself checks the active subworld, appearance state and player life. `WaterglassToken` is awarded through the Vassal’s own loot or bag and its projectile enters or exits the subworld with Infernum enabled for item use. It is a repeat route in the traced acquisition chain.

Below 60% life, Vassal starts the shark summon sequence, which creates Calamity’s `GreatSandShark` on the authoritative side. Shark override AI binds to the Vassal, inherits its combat context and participates in combo attacks. That override deactivates the shark if the Vassal is absent. This supports one Vassal arena encounter with the shark as a phase participant. Calamity’s Great Sand Shark remains a separate maintained miniboss identity, with its own `CalamityMod GreatSandShark` registration and `downedGSS` flag. Calamity’s base core use targets that shark. Infernum blocks direct core use and overrides the shark as described above, so the standalone Calamity identity does not establish independent access with Infernum active.

Infernum’s `BossChecklistManagementSystem.PostSetupContent` calls `LogBoss` for `InfernumMode BereftVassal`, passing both NPC IDs. The downed delegate reads `WorldSaveSystem.DownedBereftVassal` and the availability delegate checks `CanUseCustomAIs && NPC.downedAncientCultist`. `BereftVassal.OnKill` sets its own flag and requests sync. Its lethal-hit override instead enters a retreat animation which invokes `NPCLoot` and marks the subworld defeat state. Verify actual Checklist and world flag credit through the normal retreat, exit and reload, including whether the shark participant also advances Calamity’s separate miniboss record. Infernum also attempts to set Calamity’s Great Sand Shark progression value to 17.7 at load through the private progression dictionary. This is an order-value adjustment. Keep the separate Calamity miniboss registration and the joint Vassal NPC membership. There is no evidence for another standalone entry for the summoned shark instance.

## WoTM Checklist and Boss Rush

`BossChecklistCompatibility.PostSetupContent` looks up the loaded Checklist mod and calls `ChangeDraedonDespawnMessage`. The pinned `BossChecklist.EntryInfo.GetDespawnMessage(NPC)` signature exists. WoTM installs a detour which returns null for AresBody, ThanatosHead, Artemis and Apollo and delegates other NPC types to the original. This changes message behavior around existing entries. The inspected path creates no key, edits no entry or NPC list, and supplies no completion or availability override. The detour’s effective behavior in a pinned launch is unverified.

`WoTM.PostSetupContent` iterates `CalamityMod.Events.BossRushEvent.Bosses`. Its callback matches the entry whose `EntityID` is Calamity’s `Draedon` and appends `WoTM/AresHand` to `HostileNPCsToNotDelete` (callback IL_0001–0018). This is a cleanup exemption on an existing roster entry. Within the inspected WoTM references, there is no insertion, removal, reorder or spawn-delegate replacement. Infernum’s `BossRushChangesSystem` also writes the roster during setup and switching. The final roster, which list instances retain WoTM’s exemption and actual cleanup behavior remain unverified. Calamity Hunt’s independently documented Old Duke removal and Goozma insertion still stand as a separate roster edit. [Hunt review](review-1-1d-b.md#compatibility-and-limits-of-acceptance)
